第一部分　整体图景

1.1 这个后端到底是什么

一句话：一个一直运行着的程序，监听 5237 端口，等着前端发 HTTP 请求，帮它查数据库、算业务规则、把结果转成 JSON 回过去。

系统里有三个角色：

为什么前端不直接连数据库？ 三个原因，也是后端的全部价值：

  1. 权限：谁能看什么、谁能改什么，只有后端能可靠判断（前端的按钮隐藏只是”好看”，不是”安全”）。
  2. 业务规则：比如”这个供应商被采购单引用过就不许删除”，这种判断必须放在后端。
  3. 并发：两个人同时改同一条数据，得有人负责拦下后保存的那个。

每个业务模块内部都是同一个套路（以 MasterData 为例）：

1.3 依赖方向：只能往下，不能回头

规矩：

  • Service 里绝不允许出现 HttpContext、Request、Response、状态码数字。因为 Service 是纯业务，它不知道自己是被人从网页调的、还是被定时任务调的。
  • Controller 里绝不允许出现 _db.Suppliers.Where(...)。一旦 Controller 直接查库，权限校验、审计、并发全都会漏。
  • 判断依据很简单：如果你在 Controller 里看到 if (供应商已存在) throw，那就是写错了位置。

2.11 async / await

  • async → 这个方法里有”等待”操作
  • await → “在这里等它，等的时候线程可以去干别的”
  • Task / Task<T> / ValueTask → “一个将来会有结果的东西”

作用：处理请求时如果卡在数据库 IO 上，线程不会被白白占住，能去接待别的请求。这就是”一个服务器能撑几百个并发”的关键。

⚠️ 你现在的项目里，Service 层全是同步方法（GetList、Create… 都没有 async）。
这在内部系统里能跑，但接口一多，高并发时会明显吃线程。规范做法是全部改成 async Task<T> + await ...ToListAsync()。这是一个已知的技术债，不是 bug。

3.3 中间件管道：顺序不能乱

中间件 = 流水线上的工位。请求从 ① 走到 ⑧，响应再从 ⑧ 退回 ①。

最后：三个判断口诀

看不懂一个文件时，用这三句话定位：

1. 这个文件在 12 步的哪一步？
Controller 在第 7 步、Service 在第 8-10 步、拦截器在第 9 步、中间件在第 3 步。

2. 它属于”名词”还是”动词”？
Entities / Dtos 是名词（描述形状）；Services / Controllers 是动词（做事）。

3. 我要改的东西，是”数据形状”还是”业务规则”？
改形状（加字段）→ Entity + Dto + 迁移；
改规则（加限制）→ 只改 Service。
