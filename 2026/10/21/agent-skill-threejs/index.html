从零制作一个 Agent Skill：以 Three.js 网页建模为例

发表于2026-10-21|更新于2026-10-21|技术实践
|总字数:3.2k|阅读时长:10分钟|浏览量:

什么是 Agent Skill

Agent Skill 是一份写给 AI 的工作说明书，以 SKILL.md 为核心文件。Anthropic 将其定义为”有组织的指令、脚本和资源文件夹，Agent 可以动态发现并加载，以在特定任务上表现更好”。它把通用 Agent 变成针对特定需求的专用 Agent。

一个 Skill 最少只需要一个文件夹加一个 SKILL.md。文件开头必须是 YAML frontmatter，包含 name 和 description 两个必填字段。Agent 启动时预加载所有已安装 Skill 的元数据，这是渐进式披露的第一层：元数据只提供足够信息让 Claude 判断何时该用这个 Skill，而不加载全部内容。只有当 Claude 认为该 Skill 与当前任务相关时，才会读取完整的 SKILL.md 正文。

复杂 Skill 可以拆分到 references/、scripts/、assets/ 等子目录，在 SKILL.md 中用相对路径引用。Claude 会在需要时再打开这些文件，这是渐进式披露的第三层。这意味着一个 Skill 能容纳的上下文实际上是无限的，Agent 不需要一次性读完全部内容。

打包与分发

通用 Agent Skills 的打包方式是将 Skill 文件夹压缩为 ZIP。压缩时 ZIP 的顶层目录应该直接是 SKILL.md，而不是把 SKILL.md 再套一层文件夹。Claude Code 官方文档给出了 Skill 的存放位置规范：个人 Skill 放在 ~/.claude/skills/<skill-name>/SKILL.md，对所有项目可用；项目级 Skill 放在 .claude/skills/ 下，跟随仓库分发。Skill 的目录名或 frontmatter 中的 name 决定了调用命令的名称。

制作 Skill 的通用方法

先确认任务是否适合 Skill 化

Anthropic 的建议是从评估开始：先让 Agent 在代表性任务上运行，观察它在哪些地方卡住或需要额外上下文，然后有针对性地构建 Skill 来填补这些缺口。适合 Skill 化的任务通常满足：反复执行、输入输出明确、步骤可描述、结果可校验。一次性、高度探索性的任务用普通 Prompt 更合适。

description 只写触发条件

阿里云开发者社区分析 Superpowers 框架时指出一个关键发现：description 只应描述触发条件，绝不要总结 Skill 的工作流程。测试发现，如果 description 概括了工作流，Agent 可能直接按 description 执行，跳过阅读完整的 SKILL.md 正文，导致规则被绕过。例如：

正文只放核心流程和硬性规则

SKILL.md 正文应该精简。Claude Code 文档的示例中，一个完整的 Skill 正文只有几行：动态注入当前 git diff，然后要求 Claude 用两到三个要点总结变更，列出风险。description 中写清了触发场景，正文只做实际工作。

详细的领域知识、参考文档、示例应该放到子文件中，让 Agent 在需要时再读取。Anthropic 的 PDF Skill 就是把表单填写指令拆到 forms.md，核心 SKILL.md 保持精简，Claude 只在处理表单时才读那个文件。

把确定性交给代码

Claude Code 的 Skill 支持动态上下文注入：在 SKILL.md 中写 !command ，Claude Code 会在把内容交给 Claude 之前执行命令并替换为输出。Skill 也可以打包 Python 脚本，Claude 直接执行脚本而不把脚本或数据加载到上下文中。Anthropic 指出，用 token 生成来排序列表比直接运行排序算法昂贵得多，而且代码提供了确定性的可靠性。

测试与迭代

准备 3 到 5 个有代表性的输入，分别对比无 Skill 和有 Skill 的输出质量。如果某个环节 AI 反复出错，要么规则不够硬，要么那个环节应该直接做成脚本。Superpowers 框架的测试方法论甚至用压力场景加子代理来测试纪律执行型 Skill：让 Agent 在没有 Skill 的情况下面对诱导场景，观察它是否违反规则，然后针对性地加强 Skill 的约束。

我的 Three.js 建模 Skill：设计与实现

目标定位

我想做一个能生成”完整、细节精美、配色好看的卡通人物或建筑”的 Skill。初版设计思路是：让 AI 先用 JSON 写规格（部件树、细节清单、色板），然后分五个阶段推进：规格、Blockout、Structure、Material、Surface，每阶段自查通过才能进入下一阶段。材质强制使用 PBR，颜色必须来自声明的色板，细节清单里的每一项必须映射到真实几何体或材质参数。

实际效果

跑出来的结果不理想。卡通人物像乐高积木拼的，建筑全是直角堆叠，配色虽然符合色板但整体观感僵硬。

失败复盘：问题出在哪里

第一层问题：规则太多，AI 走了捷径

description 里写了”输出单文件 HTML”，正文里又有五阶段流程。AI 很可能在读到 description 时就形成了”我要写一个 Three.js 场景”的印象，然后在正文中快速扫过阶段名称，直接开始写代码，跳过了每个阶段的自检。Superpowers 的发现正好对应这个情况：description 概括工作流会导致 Agent 跳过 Skill 正文。我的 description 虽然没有详细总结五阶段，但”生成卡通人物或建筑模型”这个概括本身就暗示了一条简单路径：找几何体、拼起来、加点颜色。

第二层问题：工具本身的精度上限

更根本的问题是路线选择。Three.js 官方示例里视觉质量高的场景，通常走两条路。第一条是加载外部模型：在 Blender、Maya 等 DCC 工具中由美术制作好 GLB/GLTF，Three.js 只负责加载和渲染。Google Maps 的 WebGL Overlay 示例就是标准做法：创建 GLTFLoader，加载 .gltf 文件，把 gltf.scene 加入场景，然后配置相机和光照。第二条是 Shader 风格化：用自定义着色器给模型加上手绘感或卡通感，但底下仍然需要结构合理的模型。

纯用 BoxGeometry、SphereGeometry 从零拼装，精度上限就是低多边形积木。three-low-poly 这个 npm 包的存在本身就说明了问题：它的定位是”通过程序化生成几何体、预制模型、工厂工具来创建风格化低多边形场景”，并且明确说”大多数采用者会导入自己的 glTF 资产，把这个库当作场景增强而非建模软件的替代”。程序化几何体适合的是低多边形美学、抽象场景、数据可视化，不是精细卡通人物。

第三层问题：缺少视觉反馈闭环

我的 Skill 里写了每阶段自检，但没有规定如何自检。AI 只能根据文字判断”我做了这个步骤”，无法知道自己做出来的东西到底长什么样。Anthropic 的 PDF Skill 之所以可靠，是因为它包含一个预写的 Python 脚本，直接读取 PDF 并提取表单字段，结果是确定性的。我的 Skill 没有类似的确定性验证环节，AI 的自检变成了自我安慰。

如果重做：Skill 流程应该怎么改

方案一：改为编排”资产 + 渲染”管线

Skill 不负责从零建模型，而是指导 AI 完成以下流程。

第一步，生成或获取 GLB 资产。可以用图生 3D 工具根据参考图生成，也可以让用户提供现成模型。腾讯云混元生 3D 的实践案例展示了这条路径：用文生 3D 或图生 3D 生成 GLB 模型，然后搭配 Three.js 在网页端做 GLB 模型加载、动态旋转预览。混元生 3D 的输出格式是 GLB/GLTF，直接兼容 Three.js，不需要格式转换。

第二步，在 Three.js 中加载和渲染。这里才是 Three.js 发挥价值的地方：用 GLTFLoader 加载模型，配置 MeshStandardMaterial 或 MeshPhysicalMaterial 的 PBR 参数，设置环境光照，启用色调映射，添加后处理。Google Maps 的示例展示了最简加载流程：创建 loader、加载模型、scene.add(gltf.scene)、配置相机矩阵。

第三步，交互和动画。相机控制、点击交互、骨骼动画播放。Superpowers 框架的 Skill 设计强调每个 Skill 只做一件事、可组合。所以可以拆成两个 Skill：一个负责加载和展示 GLB，一个负责给 GLB 添加交互和动画。

这条方案的关键改动是：SKILL.md 中不再出现”生成几何体”的指令，取而代之的是”调用 GLB 加载器”。硬性规则改为：禁止用 BoxGeometry 或 SphereGeometry 拼装人物或建筑主体；材质必须使用 PBR 材质并配置环境贴图；必须验证模型能正常渲染且无控制台报错。

方案二：如果坚持代码建模，接受风格化而非精美

如果一定要纯代码生成，目标必须从”精美卡通人物”改成”风格化低多边形场景”。three-low-poly 的设计哲学可以作为参考：程序化生成几何体，参数化控制尺寸、颜色、细节，预制模型直接 scene.add()，工厂函数批量组装。它明确说低多边形描述的是美学，选择这条路线就要接受它的视觉风格。

在这个方案下，SKILL.md 的硬性规则应该包括：禁止试图程序化生成写实或精致卡通人物；所有几何体必须使用低多边形风格（flatShading: true，控制面数）；颜色使用受限的调色板，不允许渐变或复杂纹理；场景必须有统一的氛围层（雾、光照、粒子效果）来弥补单件模型的简陋感。这样产出的东西至少是风格统一的低多边形场景，而不是精细度不够的失败品。

一个更根本的教训

制作 Skill 的通用流程并不复杂：明确边界、拆解流程、写好 SKILL.md、把确定性逻辑脚本化、反复测试。但选对路线比写细规则更重要。

Anthropic 在介绍 Agent Skills 时强调，Skill 的价值在于将专业知识打包成可组合的资源，让通用 Agent 变成专用 Agent。但专业知识的前提是：那个领域本身有可行的专业路径。让 Three.js 纯代码拼装卡通人物，就像让一个没有雕塑训练的人用乐高积木复刻手办。积木本身没有错，但积木的精度上限就在那里。Skill 可以做的是引导 Agent 走正确的管线（生成 GLB、Three.js 渲染），而不是强迫它用错误的工具完成不可能的任务。

如果重写这个 Skill，我会把 description 改成只描述触发条件：”当用户要求用 Three.js 展示 3D 模型、制作网页 3D 场景、或将 GLB/GLTF 模型嵌入网页时使用。”正文只写两步：第一步，用图生 3D 工具或用户提供的文件获取 GLB 资产；第二步，在 Three.js 中加载、打光、渲染、添加交互。禁止用基础几何体拼装主体模型的规则单独列一条，并说明原因：”程序化基础几何体适用于抽象和低多边形风格，不适合精细卡通人物或写实建筑。”这样 AI 不会在错误的路径上浪费精力，产出质量也能稳定在可接受的范围内。
